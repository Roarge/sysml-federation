V4 Deployment

one container, one process tree, one port, and how the image is built and published

The process tree

One binary is PID 1 and everything else runs under it: the three gqlgen subgraphs as goroutines on loopback ports, the vendor router as a child process, and the UI server on the one published port (AD-0010, AD-0011). The supervisor is the router's direct parent and reaps it through os/exec without tini (C-58). Subgraphs start first, each waited for on its health endpoint, then the router until /health/ready answers on its loopback port, then port 8080 opens.

Offline by construction

No connection leaves the container while it runs (SR-03). The four telemetry variables are baked into the image with ENV (AD-0013), and the supervisor adds the listen address, the playground path and the path of the copied configuration, so the router needs no YAML file of its own. Whether it starts from environment alone in a distroless image is C-20's spike. Its licence text is fetched at build time from the vendor's repository at the pinned tag, with a pinned checksum, so it cannot drift from the binary (SR-07).

Subcommands

serve is the default and runs everything in the tree. adapter, capacity, document and ui each run one component on a given address, for anyone who wants to see the services apart. healthcheck GETs the router's /health/ready on its loopback port and /viewer on the published port, and exits non-zero if either fails. That is what the image's HEALTHCHECK calls, since a distroless image has no shell to run anything else (C-55).
